# Changelog

## Unreleased

### Added

- Contracts at `contracts.services.<service>`, each with an `enable` and a required static or dynamic `identity`.
- Claim kinds `binds`, `mounts` and `secrets`, whose mount and secret owners and groups default from the service's identity, and whose secrets name the generator of a value the service makes on its own in `generate` and leave the rest of their values to the backend, with read-only claim sets at `contracts.claimSets.<kind>` and clash checks in `contracts.assertions`. A further check fails when a dynamic identity cannot read its secrets, whether or not a backend is imported, and one when a secret's `generate` names a generator no backend adapter provides. A secret's `path` is never null: without a secret backend adapter, reading a `path` or serialising `contracts.claimSets.secrets` fails with an error naming the missing adapter, so import one first.
- `contracts.kinds.mounts.classes`, and the adapter slots `contracts.kinds.secrets.backend`, with the backend's `location` and `generators`, and `contracts.kinds.secrets.delivery`, with the delivered `path`. Each slot is null until its adapter is imported and takes one definition, so a second backend or delivery adapter fails once the slot is read, naming both.
- `lib.mkClaimKind`, for defining further claim kinds with their own clash and check rules and their own settings under `contracts.kinds.<name>`, which the check rule reads. A kind may take any name except `enable` and `identity`, the contract's own fields.
- `lib.mkDefaultContract`, for contracts a node can override field by field, including claims held under `lib.mkIf` or `lib.mkMerge`.
- `lib.types.tag`, which takes the tag declarations of `lib.types.attrTag` and settles definitions that name different tags by priority: the tag whose strongest definition is strongest wins, a definition counting at its strongest leaf, each leaf at its innermost override, and the other tags' definitions are dropped. A false `lib.mkIf` contributes no priority. Two different tags at one priority still fail, naming the option. A contract's `identity` has this type, so a node switches a module's static identity, written through `lib.mkDefaultContract`, to a dynamic one, or a dynamic one to a static one, by writing the other tag at normal priority, and a project's claim kind gets the same switching for its own tags.
- Checks in `contracts.assertions`, written without the library's prefix, and the read-only `contracts.failures`, the prefixed messages of the failed ones.
- `nixosModules.default`, which forwards the failed checks to NixOS `assertions`, and `modules.generic.default` for any module class.
- Examples for a static-identity service (influxdb2), a dynamic-identity service (alloy) whose secrets a feature module adds, a helper daemon with a contract of its own (the chrony exporter) and a project-defined claim kind, evaluated by the checks.
- Adapters `nixosModules.preservation` (mounts into `preservation.preserveAt` by class root), `nixosModules.agenix-rekey` (secrets into `age.secrets` with their owner, group, mode and generator, the rest of a value set on the same entry, the `contracts.kinds.secrets.backend` slot from `age.secrets` and `age.generators`, and a check for a secret without an encrypted file), and `nixosModules.systemd-credentials` (a dynamic identity's secrets into its unit's `LoadCredential=`).
- A secret's `from`, a list of references to the secrets its value comes from. Without `generate` the secret is a copy; with it, the generator makes the value from the referenced secrets. A reference names one claim by `{ node; kind; service; id; }` and always names its node, so it means the same claim on every node that reads it, and every claim carries its own as the read-only `ref`, built from the configuration's node identity at `contracts.node`. The read-only `contracts.lookup` and `contracts.resolve` find the claim a reference names, of any kind, in the configuration itself or in the node collection `contracts.nodes`. The core resolves each of a secret's references into its read-only `referenced`, each the reference's fields with its `claim`, with one check per reference for an unknown node, a node without nixos-contracts, an unknown claim kind, a claim of no enabled contract, and a referenced secret with `from` of its own, a check for several references without `generate`, and a check for a `contracts.node` missing from a non-empty node collection, all with or without a backend. The agenix-rekey adapter turns the resolved claims into the copy's `rekeyFile` and the generator's `dependencies`, with a check for a referenced node without the adapter. `lib.types.reference`, the type of a reference of any kind, and `lib.types.referenceTo`, of a reference of one kind whose `kind` defaults to it and accepts no other, let a service module's settings carry a reference; `from` takes `referenceTo "secrets"`, so a reference of another kind fails as a type error. `nixosModules.cross-config` defaults `contracts.node` and `contracts.nodes` from nixos-cross-config. An example shares one token between two nodes.

### Migration

- A service module that names a secret's generator on the backend, as in `age.secrets.<service>-<id>.generator.script = "alnum";`, names it on the claim instead: `secrets.<id>.generate = "alnum";`.
- A configuration that copies another configuration's secret by writing `age.secrets.<name>.rekeyFile` and the receiver's group, mode and installed path on the sender's side declares a copy on the receiving service instead, as `secrets.<id>.from = [ { node = "<sender>"; name = "<service>-<id>"; } ]`, and gives the configuration its node collection at `contracts.nodes`. A generator's dependencies set on `age.secrets.<name>.generator.dependencies` move to the claim's `from` the same way.
- A node that switched a module's identity to its other tag with `lib.mkForce`, as in `identity = lib.mkForce { dynamic.unit = "chronyd.service"; };`, may drop the `lib.mkForce` and write `identity.dynamic.unit = "chronyd.service";`; the forced form still works. A claim kind that declares a field with `lib.types.attrTag` declares it with `lib.types.tag` to switch the same way.
- A `lib.mkClaimKind` check rule receives `settings` and `config` beside `identity` and `claim`, so a rule written as `{ identity, claim }:` must accept them, for example as `{ identity, claim, ... }:`. It may return a list of reasons, each reported as its own failure. A claim that passes its kind's check rule adds no entry to `contracts.assertions`, so a module that counted the entries reads `contracts.failures` instead.
- A configuration that set `contracts.adapters.agenix-rekey.nodes` sets `contracts.nodes` instead. A module that read the reference checks' messages finds them as secrets kind checks, such as ``secrets claim `influxdb-token`: it references node `metrics`, which is not in `contracts.nodes`.``
- A node that adds generators by defining `contracts.kinds.secrets.generators` beside a backend adapter adds them to the backend instead, such as to `age.generators`.
- Kind settings move from `contracts.<kind>` to `contracts.kinds.<kind>`. A node that sets `contracts.mounts.classes` sets `contracts.kinds.mounts.classes` instead, and a module that reads or sets the secrets kind's `location`, `delivery` or `generators` finds them under `contracts.kinds.secrets`. A claim type of a project's kind that reads its settings as `config.contracts.<name>` reads `config.contracts.kinds.<name>`.
- `contracts.kinds.secrets.location`, `generators` and `delivery` move into the adapter slots `contracts.kinds.secrets.backend = { location; generators; }` and `contracts.kinds.secrets.delivery = { path; }`. A backend adapter sets its location and generators in one definition of `backend`, and a delivery adapter its function as `delivery.path`. A module that reads `location` reads `backend.location`, which fails while `backend` is null. A node that replaced one of the options with `lib.mkForce` replaces the whole slot instead, as `contracts.kinds.secrets.backend = lib.mkForce { location = …; generators = …; };`, since forcing `backend.location` alone is a second definition of the slot.
- A reference written as a claim name, or as `{ node; name; }`, is written as `{ node; service; id; }` in a field of one kind, such as a secret's `from`, and as `{ node; kind; service; id; }` where any kind is taken: `"alloy-loki-password"` becomes `config.contracts.services.alloy.secrets.loki-password.ref` and `{ node = "metrics"; name = "telegraf-token"; }` becomes `{ node = "metrics"; service = "telegraf"; id = "token"; }`. A reference always names its node, so a configuration that references a claim of its own, or reads a claim's `ref`, sets `contracts.node` to its name in the node collection, or imports `nixosModules.cross-config` beside nixos-cross-config to take it and `contracts.nodes` from there.
- A setting typed `lib.types.reference` that takes references to one kind, such as a receiver's writer tokens, is typed `lib.types.referenceTo "<kind>"` instead; `lib.types.reference` now requires `kind`. A sender passes its claim's `ref` into it rather than building a reference from its node identity and claim name.
- A module that read `node` and `name` from an entry of a secret's `referenced` reads `node`, `kind`, `service` and `id`, and the claim name from the entry's `claim.name`. A module that read another node's claims from `contracts.nodes.<node>.config.contracts` directly resolves a reference with `contracts.resolve` instead.
