# Changelog

## Unreleased

### Added

- Contracts at `contracts.services.<service>`, each with an `enable` and a required static or dynamic `identity`.
- Claim kinds `binds`, `mounts` and `secrets`, whose mount and secret owners and groups default from the service's identity, and whose secrets hold where their value comes from as the tag `value`, `provided = { }` by default, `generated = "<generator>"` for a value the service makes on its own, `copied = <reference>` for a copy of one other secret, or `derived = { generator; from; }` for a value a generator makes from the secrets it references, and leave the rest of their values to the backend, with read-only claim sets at `contracts.claimSets.<kind>.<service>.<id>` and clash checks in `contracts.assertions`. A further check fails when a dynamic identity cannot read its secrets, whether or not a backend is imported, and one when a secret's `value.generated` or `value.derived.generator` names a generator no backend adapter provides. A secret's `path` is never null: without a secret backend adapter, reading a `path` or serialising `contracts.claimSets.secrets` fails with an error naming the missing adapter, so import one first.
- `contracts.kinds.mounts.classes`, and the adapter slots `contracts.kinds.secrets.backend`, with the backend's `path` and `generators`, and `contracts.kinds.secrets.delivery`, with the delivered `path`. Each slot is null until its adapter is imported and takes one definition, so a second backend or delivery adapter fails once the slot is read, naming both.
- `lib.mkClaimKind`, for defining further claim kinds with their own clash and check rules and their own settings under `contracts.kinds.<name>`, which the check rule reads. A kind may take any name except `enable` and `identity`, the contract's own fields.
- `lib.mkDefaultContract`, for contracts a node can override field by field, including claims held under `lib.mkIf` or `lib.mkMerge`.
- `lib.types.tag`, which takes the tag declarations of `lib.types.attrTag` and settles definitions that name different tags by priority: the tag whose strongest definition is strongest wins, a definition counting at its strongest leaf, each leaf at its innermost override, and the other tags' definitions are dropped. A false `lib.mkIf` contributes no priority. Two different tags at one priority still fail, naming the option. A contract's `identity` has this type, so a node switches a module's static identity, written through `lib.mkDefaultContract`, to a dynamic one, or a dynamic one to a static one, by writing the other tag at normal priority, and a project's claim kind gets the same switching for its own tags. A secret's `value` has it too, so a node makes a module's generated secret provided by writing `value.provided = { }`, or a copy by writing `value.copied = <reference>`, and a misspelt tag, such as `value.generate`, fails as a type error.
- Checks in `contracts.assertions`, written without the library's prefix, and the read-only `contracts.failures`, the prefixed messages of the failed ones.
- `nixosModules.default`, which forwards the failed checks to NixOS `assertions`, and `modules.generic.default` for any module class.
- Examples for a static-identity service (influxdb2), a dynamic-identity service (alloy) whose secrets a feature module adds, a helper daemon with a contract of its own (the chrony exporter) and a project-defined claim kind, evaluated by the checks.
- Adapters `nixosModules.preservation` (mounts into `preservation.preserveAt` by class root), `nixosModules.agenix-rekey` (secrets into `age.secrets` with their owner, group, mode and generator, the rest of a value set on the same entry, the `contracts.kinds.secrets.backend` slot from `age.secrets` and `age.generators`, and a check for a secret without an encrypted file), and `nixosModules.systemd-credentials` (a dynamic identity's secrets into its unit's `LoadCredential=`).
- References from a secret's value to the secrets it comes from: one in `value.copied`, and a list in `value.derived.from`, which defaults to `[ ]`. A reference names one claim by `{ node; kind; service; id; }` and always names its node, so it means the same claim on every node that reads it, and every claim carries its own as the read-only `ref`, built from the configuration's node identity at `contracts.node`. The read-only `contracts.lookup` and `contracts.resolve` find the claim a reference names, of any kind, in the configuration itself or in the node collection `contracts.nodes`. The core resolves each of a secret's references into its read-only `sources`, each the reference's fields with its `claim`, with one check per reference for an unknown node, a node without nixos-contracts, an unknown claim kind, a claim of no enabled contract, and a referenced secret that is copied or derived itself, and a check for a `contracts.node` missing from a non-empty node collection, all with or without a backend. The agenix-rekey adapter turns the resolved claims into the copy's `rekeyFile` and the derived value's generator `dependencies`, with a check for a referenced node without the adapter. `lib.types.reference`, the type of a reference of any kind, and `lib.types.referenceTo`, of a reference of one kind whose `kind` defaults to it and accepts no other, let a service module's settings carry a reference; `value.copied` and `value.derived.from` take `referenceTo "secrets"`, so a reference of another kind fails as a type error. An example shares one token between two nodes.
- Claims sent between nodes through inboxes ([ADR-0015](docs/adr/0015-carry-claims-between-nodes-through-inboxes.md)). A claim of every sendable kind names the inboxes it is sent to in `sendTo`, a list of `lib.types.referenceTo "inboxes"`, on other nodes or its own. A kind `lib.mkClaimKind` builds with `sendable = false`, as the shipped kind `inboxes` is, has no `sendTo`. The claim kind `inboxes` takes claims of one `kind`, `secrets` by default, and shows what arrived from enabled contracts as the read-only `received`, `<node>.<service>.<id>` of `{ ref; claim; copy; }` with the sent claim's reference and claim-set entry, and `refs`, its references sorted by label. An inbox receives nothing while its contract is disabled. A send fails a check on the sending node for each reason `contracts.lookup` gives for the inbox and for an inbox of another kind, and an inbox fails one for a kind its node lacks, for a kind that is not sendable, such as `inboxes`, and for a `copy` on a kind other than secrets. An inbox of secrets whose `copy` is set holds a copy of each secret it receives, read as `received.<node>.<service>.<id>.copy`: a secret claim of the receiving service, owned according to its identity, with the `copy` settings applied, `value.copied` set to the sent secret's `ref` and the location `[ <service> <inbox> <node> <sender service> <id> ]`. A misspelt setting in `copy` fails at its definition, offering the closest option, whether or not anything arrived. Each copy passes the secrets kind's checks, so one its dynamic identity cannot read and one of a secret that is itself copied or derived fail. The agenix-rekey adapter installs every copy under its location joined with `_`, its `rekeyFile` defaulting to the sent secret's on the sender's node, and the systemd-credentials adapter delivers a dynamic identity's copies into its unit. The shared-token example sends telegraf's token to an influxdb inbox.
- `contracts.checkSends`, off by default, which evaluates the node a second time with every inbox empty and fails a check naming each claim whose `sendTo` or existence depends on an inbox's `received` or `refs`, where such a send otherwise recurses without a message. Each node with it on is evaluated twice, so turn it on in CI, for example. When no send depends on what arrived, it changes no send and nothing received.

### Changed

- **Breaking:** A claim is placed by its location and named from it ([ADR-0014](docs/adr/0014-name-a-claim-by-its-location.md)). Claim sets are nested by service and id, as `contracts.claimSets.<kind>.<service>.<id>`, and every claim holds a read-only `location`, `[ <service> <id> ]`, and a read-only `name`, `<node>_<service>_<id>`, which is null while `contracts.node` is null. Service names and node identities may contain only lowercase letters, digits and hyphens, claim ids also `_` ([ADR-0017](docs/adr/0017-allow-an-underscore-in-a-claim-id-and-name-a-claim-without-a-location.md)), and any other name fails at evaluation, naming it and its allowed characters. The agenix-rekey adapter names each `age.secrets` entry, and the systemd-credentials adapter each credential, by the location joined with `_`, such as `influxdb_admin-token`. Check messages name a claim by its location joined with `.`, such as ``secrets claim `influxdb.admin-token` ``. The secret backend slot's `location` becomes `path`, a function of a location, and the delivery slot's `path` takes `{ unit, location }`. The `claimName` module argument and the check that no two claims share a claim name are removed, since no two locations make one name.
- **Breaking:** The constructor declares `sendTo` on every claim of a kind other than inboxes, or any kind built with `sendable = false`, so a claim type cannot declare an option of that name, and the shipped kind `inboxes` takes that kind name.

### Migration

- A service module that names a secret's generator on the backend, as in `age.secrets.<service>-<id>.generator.script = "alnum";`, names it on the claim instead: `secrets.<id>.value.generated = "alnum";`.
- A secret's `generate = "<name>"` becomes `value.generated = "<name>"`, and a node's `generate = null`, which turned a module's generator off, becomes `value.provided = { }`. A module that read a claim's `generate` reads `value.generated or null`.
- A configuration that copies another configuration's secret by writing `age.secrets.<name>.rekeyFile` and the receiver's group, mode and installed path on the sender's side declares a copy on the receiving service instead, as `secrets.<id>.value.copied = { node = "<sender>"; service = "<service>"; id = "<id>"; }`, and gives the configuration its node collection at `contracts.nodes`. A generator's dependencies set on `age.secrets.<name>.generator.dependencies` move to the claim's `value.derived = { generator = "<name>"; from = [ … ]; }` the same way.
- A node that switched a module's identity to its other tag with `lib.mkForce`, as in `identity = lib.mkForce { dynamic.unit = "chronyd.service"; };`, may drop the `lib.mkForce` and write `identity.dynamic.unit = "chronyd.service";`; the forced form still works. A claim kind that declares a field with `lib.types.attrTag` declares it with `lib.types.tag` to switch the same way.
- A `lib.mkClaimKind` check rule receives `settings` and `config` beside `identity` and `claim`, so a rule written as `{ identity, claim }:` must accept them, for example as `{ identity, claim, ... }:`. It may return a list of reasons, each reported as its own failure. A claim that passes its kind's check rule adds no entry to `contracts.assertions`, so a module that counted the entries reads `contracts.failures` instead.
- A configuration that set `contracts.adapters.agenix-rekey.nodes` sets `contracts.nodes` instead. A module that read the reference checks' messages finds them as secrets kind checks, such as ``secrets claim `influxdb.token`: it references node `metrics`, which is not in `contracts.nodes`.``
- A node that adds generators by defining `contracts.kinds.secrets.generators` beside a backend adapter adds them to the backend instead, such as to `age.generators`.
- Kind settings move from `contracts.<kind>` to `contracts.kinds.<kind>`. A node that sets `contracts.mounts.classes` sets `contracts.kinds.mounts.classes` instead, and a module that reads or sets the secrets kind's `location`, `delivery` or `generators` finds them under `contracts.kinds.secrets`. A claim type of a project's kind that reads its settings as `config.contracts.<name>` reads `config.contracts.kinds.<name>`.
- `contracts.kinds.secrets.location`, `generators` and `delivery` move into the adapter slots `contracts.kinds.secrets.backend = { location; generators; }` and `contracts.kinds.secrets.delivery = { path; }`. A backend adapter sets its location and generators in one definition of `backend`, and a delivery adapter its function as `delivery.path`. A module that reads `location` reads `backend.location`, which fails while `backend` is null. A node that replaced one of the options with `lib.mkForce` replaces the whole slot instead, as `contracts.kinds.secrets.backend = lib.mkForce { location = …; generators = …; };`, since forcing `backend.location` alone is a second definition of the slot.
- A reference written as a claim name, or as `{ node; name; }`, is written as `{ node; service; id; }` in a field of one kind, such as a secret's `value.copied`, and as `{ node; kind; service; id; }` where any kind is taken: `"alloy-loki-password"` becomes `config.contracts.services.alloy.secrets.loki-password.ref` and `{ node = "metrics"; name = "telegraf-token"; }` becomes `{ node = "metrics"; service = "telegraf"; id = "token"; }`. A reference always names its node, so a configuration that references a claim of its own, or reads a claim's `ref`, sets `contracts.node` to its name in the node collection, such as `config.crossConfig.name` under nixos-cross-config.
- A setting typed `lib.types.reference` that takes references to one kind, such as a receiver's writer tokens, is typed `lib.types.referenceTo "<kind>"` instead; `lib.types.reference` now requires `kind`. A sender passes its claim's `ref` into it rather than building a reference from its node identity and claim name.
- A module that read `node` and `name` from an entry of a secret's `referenced` reads `node`, `kind`, `service` and `id` from an entry of its `sources`, and the claim name from the entry's `claim.name`. A module that read another node's claims from `contracts.nodes.<node>.config.contracts` directly resolves a reference with `contracts.resolve` instead.
- A secret's `from` is removed, and its references move into `value`. A copy written as `from = [ <reference> ];` without a generator becomes `value.copied = <reference>;`. A value a generator makes from other secrets, written as `generate = "<name>"` or `value.generated = "<name>"` beside `from = [ … ]`, becomes `value.derived = { generator = "<name>"; from = [ … ]; }`. A module that read a secret's `referenced` reads `sources`, which holds the same entries, and one that read its generator reads `value.generated or value.derived.generator or null`. A node that made a module's generated secret a copy by writing `value.provided = { }` beside `from` writes `value.copied = <reference>` alone.
- Every agenix-rekey entry is renamed from `age.secrets.<service>-<id>` to `age.secrets.<service>_<id>`, and with it its default encrypted file, such as `influxdb-admin-token.age` to `influxdb_admin-token.age` under `age.rekey.secretsDir` and `age.rekey.generatedSecretsDir`. Rename the encrypted files, or move the generated ones aside and generate them again, then rekey once with `agenix rekey`, and move anything a module set on an entry, such as `age.secrets.influxdb-admin-token.rekeyFile`, to the new name. A delivered secret's credential is renamed the same way, so a daemon reads `/run/credentials/<unit>/<service>_<id>`; one that reads the claim's `path` follows without a change.
- A service name or node identity containing `_`, an uppercase letter or any character other than lowercase letters, digits and hyphens is renamed, such as `contracts.services.web_proxy` to `contracts.services.web-proxy`, and so is a claim id containing an uppercase letter or any character other than lowercase letters, digits, hyphens and `_`, such as `secrets.Host-Key` to `secrets.host-key`, with the references, files and module settings that name them. A claim id containing `_`, such as `secrets.ssh_host_ed25519_key`, keeps its name.
- A module that read `contracts.claimSets.<kind>.<service>-<id>` reads `contracts.claimSets.<kind>.<service>.<id>`, and one that listed a claim set with `lib.attrValues` flattens it, as `lib.concatMap lib.attrValues (lib.attrValues config.contracts.claimSets.<kind>)`. A module that read a claim's `name` as its `<service>-<id>` claim name reads its `location`, and a backend adapter names its entry by joining the location with `_`, as `lib.concatStringsSep "_" claim.location`. A claim type that took the `claimName` module argument reads its own `config.location` instead. A module that matched check messages finds a claim named by its location joined with `.`, such as ``binds claims `first.http` and `second.http` clash``.
- An adapter that set `contracts.kinds.secrets.backend.location = name: …` sets `backend.path = location: …`, joining the location itself, such as `path = location: "/run/agenix/${lib.concatStringsSep "_" location}";`, and a delivery adapter's `delivery.path = { unit, name }: …` takes `{ unit, location }` the same way. A module that read `backend.location "<service>-<id>"` reads `backend.path [ "<service>" "<id>" ]`, or the claim's `path`.
- A generator that names each htpasswd user after its client as `<host>+<service>-<id>` names it by the client claim's `name`, `<node>_<service>_<id>`, which joins the node identity, service and id with `_`, so no two clients across the node collection share a user name. A client's credentials change with its user name, so each client takes its new one.
- A claim type of a project's kind that declared its own `sendTo` option renames it, and a project's kind named `inboxes` takes another name. A module that compared a whole claim-set entry finds `sendTo` in it, `[ ]` by default.
- A copy of another node's secret by reference, whose reference a nixos-cross-config contribution carried to a receiver option such as `example.influxdb.writers.<writer> = <sender's token ref>` that the receiver turned into `secrets.writer-<writer>.value.copied`, becomes a send and an inbox. The sender sends the secret, as `secrets.token.sendTo = [ { node = "store"; service = "influxdb"; id = "writers"; } ];`, and drops its contribution. The receiver drops its option and its copied secrets, declares `inboxes.writers.copy = { };`, with the copied secrets' `owner`, `group` or `mode` inside `copy`, and reads each copy as `inboxes.writers.received.<node>.<service>.<id>.copy`, such as its `path`, where it read `secrets.writer-<writer>.path`. Each copy's agenix-rekey entry is named by its location, so `age.secrets.influxdb_writer-<writer>` becomes `age.secrets.influxdb_writers_<node>_<service>_<id>`; it still reads the sender's encrypted file, so no encrypted file moves, though `agenix rekey` runs once for the renamed entries, and a module that set anything on the old entry sets it on the new one. A copy within one node by `value.copied` stays as it is.
